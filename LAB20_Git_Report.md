## 1 Теоретическая часть

### 1.1 Системы контроля версий (CVS)

#### 1.1.1 Назначение систем контроля версий

Система контроля версий (Version Control System, VCS; также CVS — Concurrent Versions System, историческое название класса систем) — это программное обеспечение, которое хранит историю изменений файлов и папок проекта и позволяет управлять этой историей.

Основное назначение системы контроля версий:

- фиксировать каждое изменение проекта: кто, когда и что изменил;
- хранить все предыдущие версии файлов и возвращаться к любой из них;
- сравнивать версии между собой и видеть, какие именно строки были изменены;
- обеспечивать одновременную работу нескольких разработчиков над одним проектом;
- вести параллельные линии разработки (ветки) и объединять их;
- разрешать конфликты, возникающие при изменении одних и тех же участков кода;
- создавать резервные копии и восстанавливать проект после сбоев;
- интегрироваться с системами непрерывной интеграции и доставки (CI/CD), code review, трекерами задач.

Без системы контроля версий разработчик вынужден хранить копии файлов вида «проект_финал», «проект_финал_2», «проект_точно_финал», что приводит к путанице, потере изменений и невозможности совместной работы.

#### 1.1.2 Виды систем контроля версий

По архитектуре системы контроля версий делятся на три вида.

**Локальные системы** (RCS, SCCS) хранят историю изменений в специальном файле или каталоге на одном компьютере. Они подходят для небольших личных проектов, но не обеспечивают совместную работу и защиту от потери данных при поломке диска.

**Централизованные системы** (CVS, Subversion/SVN, Team Foundation Version Control) используют единый сервер, на котором находится хранилище с полной историей. Разработчики получают рабочие копии файлов, а изменения отправляют на сервер. Преимущество — единое хранилище и простота администрирования; недостатки — зависимость от доступности сервера и сети, а при потере сервера без резервной копии теряется вся история.

**Распределённые системы** (Git, Mercurial, Bazaar, Darcs) дают каждому разработчику полную копию репозитория вместе со всей историей. Локальные операции (коммит, просмотр истории, создание ветки, слияние) выполняются без обращения к серверу, а обмен изменениями происходит командами `push` и `pull`. Такие системы устойчивы к сбоям сервера, поддерживают работу офлайн и удобны для ветвления.

| Вид | Примеры | Хранение истории | Совместная работа |
| --- | --- | --- | --- |
| Локальные | RCS, SCCS | На одном компьютере | Отсутствует |
| Централизованные | CVS, SVN, TFVC | На общем сервере | Через сервер |
| Распределённые | Git, Mercurial | У каждого разработчика полностью | Через обмен изменениями |

#### 1.1.3 Git: особенности подхода к работе с данными и преимущества

Git — распределённая система контроля версий, созданная Линусом Торвальдсом в 2005 году для разработки ядра Linux.

**Особенности подхода Git к работе с данными:**

1. **Снимки, а не разницы.** Большинство систем хранят изменения файлов в виде набора разниц (дельт). Git при каждом коммите сохраняет снимок состояния всех файлов проекта. Если файл не изменился, Git не дублирует его, а хранит ссылку на тот же объект. Это ускоряет переключение между версиями и делает историю надёжной.
2. **Адресация по хешу.** Каждый объект (файл, каталог, коммит) имеет уникальный идентификатор — SHA-1 (в новых версиях поддерживается SHA-256). Хеш вычисляется по содержимому, поэтому незаметно изменить историю невозможно: любое изменение сразу обнаруживается.
3. **Три состояния файла.** Файл в Git может находиться в рабочей области (working directory), в области подготовленных изменений (staging area, index) или в хранилище (repository, каталог `.git`). Коммит создаётся из области подготовленных изменений, что позволяет выбирать, какие именно изменения войдут в следующую версию.
4. **Лёгкие ветки.** Ветка в Git — это всего лишь указатель на коммит. Создание и переключение веток выполняются почти мгновенно и не требуют копирования файлов проекта.
5. **Локальность операций.** Практически все операции (`commit`, `log`, `diff`, `branch`, `merge`, `status`) работают с локальной копией репозитория и не требуют подключения к сети.
6. **Целостность и неизменяемость.** История коммитов образует связный граф; изменить старый коммит, не изменив все последующие, невозможно.

**Преимущества Git:**

- высокая скорость работы;
- распределённость и независимость от сервера;
- мощное и удобное ветвление и слияние;
- целостность данных благодаря хешированию;
- возможность работы офлайн;
- широкая распространённость и поддержка платформами GitHub, GitLab, Bitbucket;
- огромная экосистема инструментов и интеграций (CI/CD, code review, GitHub Actions).

**Недостатки:** сравнительно высокий порог входа, сложность некоторых команд, необходимость Git LFS для больших бинарных файлов.

#### 1.1.4 Установка и настройка Git на ПК

1. Скачать установщик с официального сайта `https://git-scm.com/downloads` и запустить его. В составе GitHub Desktop уже поставляется Git, поэтому отдельная установка не обязательна.
2. Проверить установку командой:

```text
git --version
git version 2.56.0.windows.4
```

3. Указать имя и электронную почту, которые будут записываться в коммиты:

```text
git config --global user.name "Сойко Игнат Олегович"
git config --global user.email "hayflyf@gmail.com"
```

4. Настроить окончания строк для Windows и отображение кириллицы:

```text
git config --global core.autocrlf true
git config --global core.quotepath false
git config --global i18n.commitEncoding utf-8
```

5. При необходимости задать редактор по умолчанию и проверить настройки:

```text
git config --global core.editor "notepad"
git config --list --show-origin
```

6. Для работы с GitHub настроить аутентификацию: войти в GitHub Desktop либо создать Personal Access Token (Settings → Developer settings → Personal access tokens) и использовать Git Credential Manager. Дополнительно можно создать SSH-ключ командой `ssh-keygen -t ed25519 -C "hayflyf@gmail.com"` и добавить открытый ключ в GitHub (Settings → SSH and GPG keys).

### 1.2 GitHub

#### 1.2.1 Назначение сервиса GitHub

GitHub — облачная платформа для хранения Git-репозиториев и совместной разработки. GitHub предоставляет:

- удалённое хранение репозиториев (публичных и приватных);
- совместную работу и разграничение прав доступа;
- пул-реквесты (pull requests) и код-ревью;
- трекер задач (Issues) и проекты (Projects);
- непрерывную интеграцию и доставку (GitHub Actions);
- хостинг статических сайтов (GitHub Pages);
- пакеты (GitHub Packages), релизы, вики, обсуждения;
- социальные функции: профиль разработчика, подписки, звёзды, форки.

GitHub не заменяет Git, а дополняет его: Git — это инструмент контроля версий, а GitHub — сервис для хранения и совместной работы.

#### 1.2.2 Назначение GitHub Desktop

GitHub Desktop — официальное графическое приложение для Windows и macOS, упрощающее работу с Git и GitHub. Оно позволяет:

- клонировать репозитории и создавать новые;
- просматривать изменения файлов и формировать коммиты;
- создавать, переключать и удалять ветки;
- выполнять `push` и `pull` без командной строки;
- разрешать конфликты слияния;
- создавать пул-реквесты и переходить на страницу репозитория;
- открывать проект в Visual Studio Code или другой редактор.

GitHub Desktop удобен для начинающих, но не отменяет знание команд Git: сложные операции всё равно выполняются в консоли.

#### 1.2.3 Основные термины Git и GitHub

1. **Репозиторий (repository)** — хранилище проекта вместе со всей историей изменений. Бывает локальным (на компьютере) и удалённым (на GitHub).
2. **Рабочая область и хранилище** — рабочая область (working directory) содержит текущие файлы проекта; область подготовленных изменений (staging area/index) — изменения, отобранные для следующего коммита; хранилище (repository, каталог `.git`) — зафиксированная история. Это три состояния файлов в Git.
3. **Форк (fork)** — личная копия чужого репозитория в своём аккаунте. Форк создаётся кнопкой **Fork** и позволяет независимо разрабатывать проект, а затем предлагать изменения в исходный репозиторий через пул-реквест.
4. **Ветка (branch)** — независимая линия разработки, указывающая на определённый коммит. Позволяет вести новую функцию или исправление, не затрагивая основную ветку.
5. **Мастер (master/main)** — основная (главная) ветка репозитория. В современных проектах по умолчанию используется имя `main`, но исторически применялось `master`.
6. **Коммит (commit)** — зафиксированное состояние проекта. Коммит хранит снимок файлов, автора, дату, сообщение и хеш, а также ссылку на родительский коммит.
7. **Пул (pull)** — получение изменений из удалённого репозитория и их слияние с локальной веткой.
8. **Пуш (push)** — отправка локальных коммитов в удалённый репозиторий.
9. **Пул-реквест (pull request, PR)** — предложение внести изменения из одной ветки или форка в основную ветку. Пул-реквест позволяет обсудить изменения, провести код-ревью и выполнить слияние.
10. **Мердж (merge)** — слияние одной ветки с другой. При изменении одних и тех же строк возникает конфликт, который разрешается вручную.
11. **Кодовое ревью (code review)** — проверка кода другими разработчиками до слияния. Позволяет найти ошибки, улучшить качество и соблюсти стандарты оформления.

### 1.3 GitLab и другие системы

**GitLab** — платформа для контроля версий и DevOps, аналогичная GitHub. Отличия: возможность установки на собственный сервер (self-hosted), встроенные CI/CD-пайплайны, merge requests вместо pull requests, развитые средства безопасности и управления проектами. GitLab удобен для организаций, которым важно хранить код внутри своей инфраструктуры.

Другие распространённые платформы:

- **Bitbucket** — интеграция с Jira и Atlassian, поддержка Git и Mercurial (ранее);
- **Azure DevOps** (ранее Team Foundation Server) — репозитории, пайплайны, доски и тестирование в экосистеме Microsoft;
- **Gitea / Gogs** — лёгкие self-hosted решения с открытым исходным кодом;
- **SourceForge** — одна из старейших площадок для открытых проектов.

Все перечисленные платформы используют Git (или совместимые системы) и поддерживают основные операции: репозиторий, ветки, коммиты, push/pull, пул-реквесты и слияние.
